Understanding Django Project and App Structure

To understand how a Django web application is organised by creating a project and an app, examining the purpose of every generated file, and connecting the app to the project so that it serves a page in the browser.

Objectives

  • Distinguish between a Django project and a Django app.
  • Identify the role of manage.py, settings.py, urls.py, wsgi.py, asgi.py, models.py, views.py, admin.py, apps.py and migrations/.
  • Register an app in INSTALLED_APPS and route a URL to a view.

What is Django?

Django is a high-level Python web framework that follows the MTV (Model–Template–View) pattern. It encourages a modular layout in which one project holds configuration and many apps hold features.

Project vs App

ProjectApp
DefinitionThe whole website: configuration + a collection of appsA self-contained module that does one job (blog, accounts, polls)
Created withdjango-admin startproject mysitepython manage.py startapp blog
How manyOne per websiteMany per project; reusable across projects
Containssettings, root URLs, WSGI/ASGI entry pointsmodels, views, admin, tests, migrations

Project layout

mysite/                 ← outer folder (container, name can be anything)
├── manage.py           ← command-line utility for this project
└── mysite/             ← the actual Python package of the project
    ├── __init__.py     ← marks the folder as a Python package
    ├── settings.py     ← all configuration (apps, DB, templates, static…)
    ├── urls.py         ← root URL dispatcher ("table of contents")
    ├── asgi.py         ← entry point for ASGI (async) servers
    └── wsgi.py         ← entry point for WSGI servers (gunicorn, mod_wsgi)

App layout

blog/
├── __init__.py
├── admin.py            ← register models with the admin site
├── apps.py             ← app configuration class (BlogConfig)
├── migrations/         ← database schema history
│   └── __init__.py
├── models.py           ← data models (database tables)
├── tests.py            ← unit tests
└── views.py            ← functions/classes that handle requests

Files commonly added by the developer: urls.py (app-level routes), templates/blog/ (HTML), static/blog/ (CSS/JS/images), forms.py.

Request flow

Browser → /blog/
   → mysite/urls.py      path('blog/', include('blog.urls'))
   → blog/urls.py        path('', views.index)
   → blog/views.py       index(request) → HttpResponse / render(template)
   → (models.py ↔ database, templates/ → HTML)
   → Response → Browser
An app is only “seen” by Django after it is added to INSTALLED_APPS in settings.py. Its URLs are only reachable after the project’s urls.py includes them.

Steps for the simulation

  1. Open the Simulation tab. It starts in Demo mode: press ▶ Play and watch a project being built once from start to finish.
  2. Switch to Practice. In the terminal, create a project with django-admin startproject <name>. You choose the name, for example mysite.
  3. Expand the project in the Explorer and open manage.py, settings.py and urls.py. Read the explanation under the editor for each one. Notice the two folders with the same name.
  4. Move into the project folder (cd <name>) and create an app: python manage.py startapp <app>. Compare the app's files with the project's files.
  5. Register the app by adding '<app>', to INSTALLED_APPS in settings.py, then save (Ctrl+S).
  6. Write a view in <app>/views.py that takes request and returns an HttpResponse.
  7. Create <app>/urls.py (using + File or touch) with a urlpatterns list that maps '' to your view.
  8. In the project's urls.py, import include and add path('<app>/', include('<app>.urls')).
  9. Start the server with python manage.py runserver. Open http://127.0.0.1:8000/<app>/ in the browser pane and follow the request journey under the page.
  10. Experiment: break one connection at a time (remove the app from INSTALLED_APPS, misspell the view name in urls.py, delete the include import…). Observe Django's error each time, then fix it.
  11. Optional: complete the bonus tasks (render a template, add a model and run makemigrations and migrate).
  12. Switch to Exercise. Complete one Build task and one Debug task, and record your scores.

Instructions

Demo builds a small Django site in front of you. Press ▶ Play, or Next to go one step at a time. Click any step in the list to jump to it. Click the boxes in the request journey to open those files.

Practice gives you a real workspace: a terminal (bottom), an editor (top) and a browser connected to your own development server. Complete the tasks on the left in your own way. You choose the names, and mistakes are welcome. Django responds as it would on a real computer, and the Observations panel explains each result.

  • Terminal: type help for the command list. ↑/↓ recall commands, Tab completes names, Ctrl+C stops the server.
  • Editor: Ctrl+S saves. Tab indents; press Esc first to move focus out of the editor.
  • The running server reloads every time you save a .py file.

Exercise tests what you learned, without hints. Pick a build task (create a site from a brief) or a debug task (repair a broken project). Then press Submit for grading. The grader runs check and requests your page, like an examiner would. Tasks are random, so you can practise many times.
