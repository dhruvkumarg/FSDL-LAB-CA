Understanding Django Project and App Structure

To understand how a Django web application is organised by creating a project and an app, examining the purpose of every generated file, and connecting the app to the project so that it serves a page in the browser.

Objectives

  • Distinguish between a Django project and a Django app.
  • Identify the role of manage.py, settings.py, urls.py, wsgi.py, asgi.py, models.py, views.py, admin.py, apps.py and migrations/.
  • Register an app in INSTALLED_APPS and route a URL to a view.

What is Django?

Django is a high-level Python web framework that follows the MTV (Model–Template–View) pattern. It encourages a modular layout in which one project holds configuration and many apps hold features.

Project vs App

ProjectApp
DefinitionThe whole website: configuration + a collection of appsA self-contained module that does one job (blog, accounts, polls)
Created withdjango-admin startproject mysitepython manage.py startapp blog
How manyOne per websiteMany per project; reusable across projects
Containssettings, root URLs, WSGI/ASGI entry pointsmodels, views, admin, tests, migrations

Project layout

mysite/                 ← outer folder (container, name can be anything)
├── manage.py           ← command-line utility for this project
└── mysite/             ← the actual Python package of the project
    ├── __init__.py     ← marks the folder as a Python package
    ├── settings.py     ← all configuration (apps, DB, templates, static…)
    ├── urls.py         ← root URL dispatcher ("table of contents")
    ├── asgi.py         ← entry point for ASGI (async) servers
    └── wsgi.py         ← entry point for WSGI servers (gunicorn, mod_wsgi)

App layout

blog/
├── __init__.py
├── admin.py            ← register models with the admin site
├── apps.py             ← app configuration class (BlogConfig)
├── migrations/         ← database schema history
│   └── __init__.py
├── models.py           ← data models (database tables)
├── tests.py            ← unit tests
└── views.py            ← functions/classes that handle requests

Files commonly added by the developer: urls.py (app-level routes), templates/blog/ (HTML), static/blog/ (CSS/JS/images), forms.py.

Request flow

Browser → /blog/
   → mysite/urls.py      path('blog/', include('blog.urls'))
   → blog/urls.py        path('', views.index)
   → blog/views.py       index(request) → HttpResponse / render(template)
   → (models.py ↔ database, templates/ → HTML)
   → Response → Browser
An app is only “seen” by Django after it is added to INSTALLED_APPS in settings.py. Its URLs are only reachable after the project’s urls.py includes them.

Steps for the simulation

  1. Open the Simulation tab. The terminal starts in an empty workspace.
  2. Create a project: type django-admin startproject mysite and press Run. Observe the generated tree.
  3. Click every file in the tree and read its contents and explanation.
  4. Move into the project folder: cd mysite.
  5. Create an app: python manage.py startapp blog. Compare the app’s files with the project’s files.
  6. Register the app: click mysite/settings.py and press Add 'blog' to INSTALLED_APPS.
  7. Write a view: open blog/views.py and press Add index view.
  8. Create blog/urls.py: select the blog folder and press Create urls.py.
  9. Include the app URLs in the project: open mysite/urls.py and press Include blog.urls.
  10. Start the server: python manage.py runserver, then visit /blog/ in the mini browser.
  11. Try skipping a step (e.g. run the server before including URLs) and observe the error — this shows why each file matters.

Use Reset to start again. Type help in the terminal to list supported commands.
